Zyvor · KVM runtime intelligence

Every VM, from outside. No agent in the guest.

Shukra sits on the hypervisor and watches every QEMU/KVM workload with eBPF. The daemon joins kernel traces to the QEMU process and gives an operator a console and a CLI that say what they know, how they know it, and what they cannot see. Observe. Protect. Explain.

What it answers

Each card is a question an operator asks and the command that answers it, from the README.

Why is this VM slow?

shukractl explain ranks host-side causes over the last minute, with evidence, and lists what Shukra cannot see. no_host_cause says the cause may be inside the guest.

Why was it slow?

explain --at gives a verdict for a past moment from snapshots stored every 5 minutes, and says how coarse it is. shukractl incident writes a bundle for the ticket.

Who is the noisy neighbour?

vCPU preemption and contention: who took whose CPU, per victim, and what that VM was doing meanwhile.

Is each VM the right size?

shukractl advise flags VMs with more vCPUs than they use or that want CPU and are not getting it. Advice for a person, never an action.

What is a VM connecting to?

Connects, new UDP flows, inbound peers, DNS query names and TLS server names, seen on the VM's own tap. Each has a switch to turn it off.

Where did the packets die?

The kernel's own drop reasons on each tap, with Shukra's isolation drops subtracted, so another dataplane or a guest not reading its NIC is named.

Is a VMM misbehaving?

Tripwires on QEMU and what it starts: sensitive file opens, ptrace, mount, setns, module and kexec loads. A steady-state VMM does none.

Where may a VM connect?

Learned baselines and egress policy: audit first, then enforce with a confirm timer. The management network can never be cut off.

Is Shukra itself safe?

shukractl doctor audits exposure, what is attached and what it cannot see, worst first and each with a fix.

Eight programs

Hot paths stay in maps. The ring buffer is only for discrete events, and events a guest can cause are rate-limited on their own budgets. Details in What each program measures.

What it does not do

The README says to read this before trusting it with anything. The full list is in docs/what-it-does-not-do.md.

Host TCP is QEMU's, not the guest's

Connect events from the host are attributed to the QEMU process and are not guest-attributed. Only events seen on a VM's tap are.

No application data

It reads four things beyond headers, each with a switch: plain DNS query names, the first TLS ClientHello segment, names of files QEMU opens (never contents), and process names.

Isolation is conditional

shukractl isolate drops a VM's tap traffic only with an explicit management allow list, on Linux 6.6 or newer. Without an allow list it is refused.

Nothing acts unless you turn it on

Responses, egress policy and baselines are off until configured. A response can only isolate a VM, and by default it only proposes.

A VM it cannot see says so

User-mode networking has no tap, and doctor names it. Percentiles can read up to 2x high because they come from log2 buckets.

Past verdicts are coarse

explain --at and incident read snapshots taken every 5 minutes, and say so when nothing is stored.

How it fits

Shukra is one privileged daemon on the hypervisor, a CLI and a console that only talk to its API, and eight eBPF programs. It is a systemd unit on the hypervisor, not a Helm chart: eBPF has to run where the VMs run.

Quickstart

Go 1.27+ and Node 22 for the console.

make build
make web
./bin/shukrad -listen 127.0.0.1:30970 -web web/dist
./bin/shukractl status

If SHUKRA_API_KEY is unset, the daemon uses the dev token shukra and says so on stderr. Open http://127.0.0.1:30970 and sign in with that token. On a Mac, or any host without BTF, programs stay detached; VM discovery from /proc still works. To attach traces you need Linux, clang, bpftool and kernel BTF: see Attach traces.

Deploy to a hypervisor over SSH (it builds on the host and starts shukra.service):

./scripts/deploy-remote.sh 10.0.1.5 sus
